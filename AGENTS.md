# AGENTS.md — STM32F746 Course Project Rules for Codex

> Scope: this file governs Codex behavior for this repository and all subdirectories unless a deeper `AGENTS.md` explicitly adds stricter local rules.
>
> Project type: STM32CubeMX-generated STM32F746 GCC/CMake project developed in VS Code.
>
> Core principle: **CubeMX owns hardware configuration; Codex assists with visible, explainable source code; VS Code is the build/flash/debug workspace; Git records each verified increment.**

---

# 0. Mandatory behavior

Codex MUST read this file completely before making any change.

Codex MUST NOT:
- create a replacement STM32 project;
- delete, recreate, or hand-edit the `.ioc` file;
- bypass CubeMX by manually changing hardware configuration in generated initialization code;
- rewrite generated CubeMX files outside allowed user sections;
- silently change pin assignments, clocks, DMA, NVIC, timers, or peripheral configuration;
- complete multiple milestones at once;
- claim hardware functionality is verified when it was only compiled;
- use `Codex`, `OpenAI`, `ChatGPT`, `Claude`, `Claude Code`, `Copilot`, `AI`, or similar names as Git author/committer/co-author;
- push, force-push, rebase, amend, hard-reset, or clean the repository without explicit user approval.

If any requested implementation conflicts with these rules, Codex MUST stop before modifying the conflicting part and explain the conflict.

# 3. Source-of-truth hierarchy

The project has the following ownership hierarchy.

## 3.1 Hardware configuration truth

The `.ioc` file and STM32CubeMX are the single source of truth for:

- GPIO pin assignment;
- alternate functions;
- RCC;
- PLL;
- clock tree;
- peripheral enable/disable state;
- DMA mapping;
- NVIC configuration;
- timer mode/channel configuration;
- ADC configuration;
- ETH/RMII configuration;
- SAI configuration;
- I2C configuration;
- USART/UART configuration;
- LTDC;
- FMC;
- LwIP options generated by CubeMX;
- other MCU peripheral configuration.

Codex MUST NOT replace CubeMX configuration with handwritten initialization.

## 3.2 Generated-code truth

CubeMX-generated initialization functions represent the generated hardware setup.

Examples:

```c
SystemClock_Config();
MX_GPIO_Init();
MX_DMA_Init();
MX_ETH_Init();
MX_LWIP_Init();
MX_SAIx_Init();
MX_I2Cx_Init();
MX_TIMx_Init();
MX_LTDC_Init();
```

Codex MUST NOT silently rewrite them.

## 3.3 Application-code truth

Project behavior above the HAL/peripheral configuration belongs in user-owned application modules, preferably under `App/`.

# 4. CubeMX configuration rules

The following changes MUST be performed through STM32CubeMX:

- moving a pin;
- assigning or changing an alternate function;
- changing a timer channel;
- changing a DMA controller/stream/channel/request;
- enabling or disabling a DMA interrupt;
- changing NVIC priority;
- changing system/peripheral clocks;
- enabling a peripheral;
- changing ETH RMII configuration;
- changing SAI/I2C/UART/ADC/LTDC hardware configuration.

If Codex determines such a change is necessary:

1. STOP before implementing the hardware change.
2. Explain:
   - what CubeMX setting must change;
   - why;
   - which current resource it replaces;
   - possible resource conflicts;
   - what generated files are expected to change.
3. Wait for the user to regenerate the project with CubeMX unless the user has explicitly authorized Codex to operate that workflow.
4. After regeneration, re-inspect generated code before adapting the application layer.

Codex MUST NOT directly patch `.ioc` text.

# 5. Logical hardware naming and resource abstraction

Upper-layer code MUST depend on **logical functions**, not physical MCU pin identities, whenever practical.

## 5.1 CubeMX User Labels

Important pins should use functional CubeMX User Labels.

Preferred names:

```text
PPS_OUT
SYNC_DEBUG_OUT
AUDIO_EVENT_OUT
STATUS_LED
USER_BUTTON
```

Avoid using physical names as application concepts:

```text
PB4_OUT
PA8_TIMER
TIM3_PIN
```

Example:

Bad:

```c
HAL_GPIO_WritePin(GPIOB, GPIO_PIN_4, GPIO_PIN_SET);
```

Preferred:

```c
HAL_GPIO_WritePin(PPS_OUT_GPIO_Port,
                  PPS_OUT_Pin,
                  GPIO_PIN_SET);
```

## 5.2 Timer/peripheral abstraction

CubeMX pin labels alone do not abstract timer handles.

Application modules MUST NOT scatter code such as:

```c
HAL_TIM_PWM_Start(&htim3, TIM_CHANNEL_1);
```

throughout the project.

Use a board abstraction layer, for example:

```text
App/BSP/
├── bsp_pps.c
├── bsp_pps.h
├── board_resources.c
└── board_resources.h
```

Upper layer:

```c
BSP_PPS_Start();
```

Board mapping layer:

```c
#define PPS_TIM_HANDLE   htim3
#define PPS_TIM_CHANNEL  TIM_CHANNEL_1
```

If CubeMX later changes:

```text
PB4 / TIM3_CH1
```

to:

```text
PA8 / TIM1_CH1
```

the intended impact is:

```text
CubeMX hardware configuration
        +
App/BSP resource mapping
```

NOT:

```text
Sync/
Measure/
Network/
UI/
and many unrelated files
```

No physical-resource abstraction should be added unless it actually improves maintainability for the current project.

# 6. CubeMX-generated file protection

CubeMX-generated files may only be modified in designated user sections whenever such sections exist:

```c
/* USER CODE BEGIN ... */

/* USER CODE END ... */
```

Do not add persistent custom logic outside those regions.

Do not perform large rewrites of generated files such as:

- `Core/Src/main.c`;
- `Core/Src/stm32f7xx_it.c`;
- `Core/Src/stm32f7xx_hal_msp.c`;
- `Core/Src/system_stm32f7xx.c`;
- CubeMX-generated peripheral files;
- CubeMX-generated network glue;
- CubeMX-generated CMake support.

If a generated file does not provide a safe user section for the desired change, prefer:
1. a callback;
2. a weak-function override;
3. a user-owned wrapper;
4. a new file under `App/`;
5. another documented extension point.

If none works, explain the limitation before making a generated-code exception.

# 7. `main.c` policy

`main.c` must remain small and readable.

Its normal responsibilities are:

```text
HAL initialization
        ↓
System clock
        ↓
CubeMX peripheral initialization
        ↓
Application initialization
        ↓
Main-loop scheduling
```

Preferred conceptual structure:

```c
int main(void)
{
    HAL_Init();
    SystemClock_Config();

    MX_GPIO_Init();
    MX_DMA_Init();
    /* other CubeMX init */

    App_Init();

    while (1)
    {
        App_Process();
    }
}
```

Do not place full algorithms directly inside `main.c`.

Prefer the following ownership:

```text
App/
├── BSP/             hardware abstraction above CubeMX
├── Network/         UDP/protocol/application network logic
├── Sync/            time synchronization and clock discipline
├── Audio/           audio buffer management

├── Temperature/     temperature and sound-speed compensation
├── Calibration/     calibration data and correction

```

Keep dependencies directional when practical:

```text
Application algorithms
        ↓
BSP / service interfaces
        ↓
HAL / CubeMX-generated peripheral handles
```

Avoid circular dependencies.

# 11. Interrupt rules

Interrupt handlers must remain short.

Inside an ISR/callback, prefer:

```text
capture timestamp
copy minimal state
set flag / enqueue event
return
```

Do NOT perform expensive work in ISR context unless there is a proven requirement.

Avoid inside ISR:
- large `printf`;
- LCD drawing;
- long loops;
- correlation processing;
- network protocol processing;
- blocking HAL calls;
- delays;
- dynamic allocation.

Codex must explain any new IRQ relationship after implementation.

---

# 12. DMA rules

Every new DMA-dependent feature must document:

- peripheral;
- direction;
- DMA controller;
- stream/request/channel as generated by CubeMX;
- source/destination buffer;
- buffer length;
- normal/circular mode;
- half-complete behavior;
- complete behavior;
- IRQ/callback path.

The application must not assume DMA configuration without confirming generated CubeMX code.

---

# 13. STM32F7 cache-coherency rule

STM32F746 is a Cortex-M7 device with cache.

For DMA buffers, Ethernet descriptors/buffers, audio buffers, or other memory shared between CPU and DMA, Codex MUST consider D-Cache coherency.

Before adding cache maintenance calls, Codex MUST inspect:
- current cache enable state;
- existing Ethernet/cache handling;
- memory region placement;
- buffer alignment requirements;
- whether current HAL/middleware already performs required maintenance.

Do not add random `SCB_CleanDCache...` or `SCB_InvalidateDCache...` calls without explaining the memory ownership and direction.

Cache changes require an explicit explanation in the completion report.

---

# 14. Units and data representation

Time-sensitive project variables MUST carry explicit units in names or types where practical.

Preferred:

```c
offset_us
delay_us
timestamp_ns
distance_mm
temperature_c
sound_speed_mps
sample_rate_hz
```

Avoid ambiguous names such as:

```c
time
offset
value
dist
```

For protocol fields:
- define width;
- define signedness;
- define unit;
- define byte order when data crosses the network.

Never depend on compiler struct padding for a network packet unless packing/layout is explicitly controlled and documented.

# 19. Definition of Done for one feature

A feature is considered complete only when all applicable items pass:

```text
[ ] Implementation is limited to the current goal.
[ ] CubeMX rules were respected.
[ ] Generated-code boundaries were respected.
[ ] Code is readable and explainable.
[ ] Build succeeds.
[ ] No new unexplained warnings were introduced.
[ ] Hardware/runtime test passes when required.
[ ] Expected debug/measurement output is observed.
[ ] Relevant user changes were preserved.
[ ] Git diff was reviewed.
[ ] A Git commit was created for the verified feature.
```

If hardware validation is required but Codex cannot independently observe the hardware result, Codex MUST ask the user for the observed result before declaring the feature complete and before making a "feature complete" commit.

If the user has explicitly authorized Codex to flash/debug/read device output and Codex can actually verify the result, it may proceed based on that evidence.

# 27. Code-style expectations

- small modules;
- explicit names;
- fixed-width integer types for protocols and hardware data;

# 32. Final project principle

The intended responsibility split is:

```text
STM32CubeMX
    → pinout / clock / DMA / NVIC / peripheral configuration

CubeMX generated code
    → HAL initialization and hardware glue

App/
    → firmware behavior and algorithms

App/BSP/
    → logical-to-physical hardware abstraction

VS Code
    → edit / build / flash / debug / observe

Tools/Monitor/
    → host-side live data observation

Analysis/
    → offline experiment analysis

Docs/
    → persistent design/project knowledge

Git
    → verified incremental history

Codex
    → visible code assistance, explanation, debugging, and controlled edits

jxq
    → Git author/committer identity and final engineering decisions
```

When in doubt, preserve CubeMX regeneration safety, preserve the user's existing work, make the smallest testable change, verify it, commit it as `jxq`, and stop before the next milestone.
