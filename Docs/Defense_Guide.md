# SBCG 答辩口头稿与追问准备

<!-- doc-status: current-defense-guide; reviewed: 2026-10-23 -->

依据[真实架构与调用链](System_Architecture.md)，当前业务固件SBCG-M3.2-MAP。以下回答区分目标、已实现逻辑、已有实物证据和未完成内容。准备日期2026-10-23；可按需要用于次日答辩，不把附件中的相对日期当作新的验收记录。

## C1. 30秒回答：系统是怎么构建起来的

“我们把系统分成硬件初始化、应用服务和电脑验证三部分。CubeMX生成Core中的时钟、引脚和外设初始化，HAL提供驱动；main完成这些初始化后调用App_Init，再循环调用App_Process。App管理网络、本地PTP时间观测、温度声速和音频采集，中断只交接字节或DMA完成状态。现在单板时间映射自检已通过，双板同步、声音检测测距和LCD界面还在后续计划中。”

## C2. 1～2分钟回答：从构建到运行

“当前系统基于STM32F746G-DISCO，采用裸机主循环和中断配合的分层结构。硬件配置由SBCG.ioc和CubeMX管理，生成Core中的时钟、GPIO、DMA、USART1、I2C3、SAI2及LwIP集成。Drivers中的CMSIS和HAL，以及Middlewares中的LwIP，也是正式运行需要的代码，不能把App之外都叫测试代码。

上电后，startup_stm32f746xx.s的Reset_Handler先调用SystemInit，再准备C语言的数据区和运行环境，最后进入main。main先配置MPU、初始化HAL及主时钟和音频时钟，再初始化外设。随后App_Init建立网络、PTP观测、温度、音频和串口命令等服务，main中的while循环持续调用App_Process。

每轮App_Process先让MX_LWIP_Process收包和处理超时，再推进各项服务。UART接收和音频DMA由硬件中断触发，回调保存字节或完成块状态，前台再解析命令和统计PCM；UDP接收回调是在前台LwIP调用链内执行的。DHT11起始低电平期间，部分日志和音频观测会延后，网络处理继续执行。

目前温度采集及整数声速、音频连续采集、帧编号、本地PTP锚点和板端时间估算自检已有证据。最近120秒实物窗口中，40组估算与真实C参考和精确分数计算一致。它证明当前本地线性模型实现一致，不能代表声学到达时间或测距精度。我们还没有完成双板校时、声音检测和测距，也没有启用TouchGFX或LCD，所以现在不能演示尚不存在的界面。”

## C3. 老师可能追问的问题

| 追问 | 基于当前代码的回答 |
| --- | --- |
| 为什么分多个目录和.c/.h？ | 让职责和依赖清楚：BSP封装资源，Network管报文，Temperature管测温状态，Audio管采集/编号/时间模型，app_main只协调。头文件约定接口和类型，源文件隐藏具体状态；修改局部模块时可独立测试。不是文件越多越好。 |
| 主要功能是不是都在App？ | 大部分自有应用逻辑在App，但运行必须依赖Core启动/中断、HAL、CMSIS和LwIP。App不负责重新实现时钟/寄存器初始化，也不包含电脑采集工具。 |
| App之外是不是测试代码？ | 不是。startup负责复位入口；Core生成硬件配置；Drivers提供HAL/CMSIS；LWIP/Middlewares实现网络；链接脚本决定内存地址。这些都属于正式系统。Tests才是主机测试。 |
| CubeMX生成代码算不算核心？ | 算运行基础。main调用的MX_SAI2_Init、MX_DMA_Init等建立真实硬件配置；删掉或随意修改会破坏应用假设。我们把业务放App，是为了保留再生成安全性，不表示生成代码可有可无。 |
| main与App_Init有什么区别？ | Reset_Handler是硬件复位入口，main是C入口并完成硬件启动；App_Init只初始化业务服务。App_Process是main循环中的一轮业务推进，不是另一个线程。 |
| 系统用RTOS还是回调调度？ | 无RTOS。主循环协同调用Process函数，UART/SAI/DMA/SysTick用中断，LwIP RAW接收回调在前台执行。回调是一种调用方式，不一定是中断。 |
| 哪些只执行一次，哪些反复执行？ | 正常启动中main的外设初始化和App_Init执行一次；App_Process不断执行，各服务按tick差值节流。UART逐字节中断、DMA半满/满回调按硬件事件发生，不能写成固定1ms任务。 |
| 你们的主要测量时钟是什么？ | 设计选ETH/PTP硬件时间。HAL_GetTick的毫秒时间用于调度和日志，DWT用于短脉冲计时，不能把这些不同时间源混成已同步的测量时刻。当前PTP是LOCAL，尚未形成双板共同纪元。 |
| 电脑时间交换是不是已经完成双板同步？ | 不是。t1/t4是电脑软件时间，t2/t3是板端硬件时间；板端现在计算offset/delay观测，并未反馈调节PTP。日志SYNC=0是明确边界。 |
| DHT11为何配置成输出？为什么不接ADC？ | 单数据线数字协议需要MCU先开漏拉低发起，然后释放总线并读传感器脉冲。PG7/D4是DATA，当前供电3.3V；温度数据由数字帧解码得到，ADC不能直接读出它的温度值。 |
| 温度对测距有什么用？手动设温为何保留？ | 声速随温度变化，当前统一用整数公式计算声速，避免不同模块各算一套。手动设温用于设参/对照/异常替代，AUTO仍采真实传感器；两板共享温度还没实现。 |
| 音频DMA和CPU怎样配合？ | DMA循环写64KiB SRAM1缓冲，半满/满中断交接8192帧块状态；CPU在前台安全领取和结束验权后发布统计。DMA不会等CPU，不能无限保留块指针，发生覆盖必须报告。 |
| 为什么不能把缓冲随便放到RAM里？ | F746各RAM区对DMA的可达性不同，DMA2不能访问DTCM。当前用用户链接扩展把音频缓冲放0x20010000起，并与ETH堆/描述符和主栈分开检查。Cache当前关闭；将来打开要重新审核一致性。 |
| 三点时间估算在测距里起什么作用？ | 它先建立音频帧位置与本地PTP之间的可检查关系。当前每三锚点用两端估计中间点，验证算法和板端实现；真正声音事件还要检测、定位并补偿codec/FIFO等延迟，之后才能用于跨板TDOA。 |
| 14.884us是不是声学精度或距离误差？ | 不是。它是本次40个留出点的本地模型残差最大绝对值，不含完整声学链路偏差，不是所有未来样本的保证，也不是双板同步指标。 |
| 为什么需要多个时序门控？ | DHT起始低电平期间，前台同步串口/I2C操作可能拖延温度状态推进，所以日志可缓存，codec/音频观测延后；网络继续运行。协议脉冲读取和部分HAL操作仍会有界阻塞，不能宣称完全实时无阻塞。 |
| 删除HAL或TouchGFX会怎样？ | 当前删除所需HAL会导致缺符号或失去外设操作；TouchGFX现在未加入工程，不能说当前已经依赖它。以后若接入，才需讨论生成层/资源/View/Presenter/Model。 |
| LCD不显示怎么定位？ | 当前首先确认它尚未实现，而不是先怀疑某个View。后续应逐层验电源/时钟、FMC SDRAM读写、LTDC时序与帧缓冲、像素格式，再验绘图/GUI调度；这是一条后续调试路线，不是已有屏幕测试结论。 |
| 按键/触摸在哪里处理？ | 当前没有业务输入回调或触摸任务，只有串口温度命令。板上存在按键/触控器件不等于本固件使用了它们。I2C3当前用于codec访问，不应据同一总线就推断触控已实现。 |
| 新加功能一般改哪里？ | 先判断是否改硬件资源；需要则经CubeMX生成并检查。业务写App对应模块，BSP集中物理映射，在app_main接调度，用户CMake登记，补主机验证和本版实物验收。不能直接手改.ioc或生成区。 |
| 怎么证明不只是编译通过？ | 构建和布局只证明软件可编译链接；实物还要匹配固件SHA/UID、烧录校验、采串口和电脑实际UDP结果。本次引用的M3.2.4有120秒原始数据、40组真实C/Fraction对照及原业务复验，不靠STACK_OK单项认定对端收到。 |
| 当前离完整声波测距还差什么？ | 任意事件的时间查询/声学延迟标定、声音事件检测、双板共同时间/配对、TDOA测量与误差验收，以及LCD显示；温度共享也需后续业务。现在完成的是一块板上的采集、通信和时间观测基础。 |

## E. 建议现场打开的证据

1. `Core/Src/main.c`：指出真实外设顺序与App_Init/while App_Process入口。
2. `App/app_main.c`：说明初始化依赖、先网络后观测的主循环，以及DHT门控。
3. `Core/Src/stm32f7xx_it.c`与`App/BSP/bsp_audio.c`：把IRQ→HAL→回调→前台处理串起来。
4. `App/Audio/audio_time_map_monitor.c`和`audio_time_map.c`：区分调度/窗口状态与纯算法。
5. `Docs/Milestones/M3_2_4_Audio_Time_Map_Board.md`：展示本版实物结果与未测范围。原始日志在本机Logs，不会随Git提交。
6. `CMakeLists.txt`、`cmake/stm32cubemx/CMakeLists.txt`：说明App与HAL/LwIP同时进入固件；Tests/Tools没有被当作板端业务源码。

## F、G. 表述与演示边界

本轮只修改注释和文档，构建结果见[验证记录](Architecture_Comment_Review.md)，没有新烧录/新声学实验。现场若未另行运行采集，展示的是已归档的M3.2.4证据，不应说刚刚重新测过。长期稳定性、受控发声和拔插等历史实验各自有版本边界，不能合并成一次全项目已完成验收。

不要承诺屏幕、方向/距离数字、锁定状态或双板结果现在就能显示；先把当前实现和证据讲清楚，再解释后续每个独立目标需要怎样验证。
