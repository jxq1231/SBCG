# M2.2.4 板端实时估算观测规划

日期：2026-10-21。设计基线66bfa7b，初始工作区干净。状态：已获用户批准并完成实现、248项检查、构建/再生成及本版本授权烧录；30组板端结果与真实C逐条一致，详情见同目录Implementation及里程碑报告。本轮继续只使用当前板，不检查第二板。

## 一个目标与作用

让当前STM32主循环真正运行现有SyncEstimator_Calculate：每次专用交换结束后，电脑补交同一完整键的t1/t4，板使用自己保存的请求RX和ACK TX组成四时间戳，输出实时观测；30组板端整数结果与电脑原生C结果逐条完全一致。

M2.2.3已经完成电脑回放，本增量把计算接入实际板端运行，建立后续自主校时所需的输入、调度和错误边界。保持LOCAL/SYNC=0，不调用MAC时间更新或频率校正，不使用电脑软件时刻去宣称两板同步。

## 协议增量

原5005、5006/6006、5007/6007及type1～6不变。新消息仍是电脑192.168.10.100:6007 → 当前板192.168.10.1:5007，不增加PCB；现有三个PCB继续使用默认4个池名额。

新增type7 OBSERVATION_SUBMIT，52字节，所有整数无符号大端：

| 偏移/字节 | 字段 |
| --- | --- |
| 0～35 | 原SBCG/version1封套和完整键；TYPE=7，LENGTH=52；其余字段同本次type4请求 |
| 36/8 | T1_PC_SW_NS，电脑原请求发送前的软件时刻 |
| 44/8 | T4_PC_SW_NS，首个有效type5 ACK接收后的软件时刻 |

Python布局为`!4sBBHIIIIIQQQ`。完整键仍为SESSION+UID+SEQ+CLIENT_TICK_MS。板检查来源、长度、非零身份及t1导出的tick与键一致；t1/t4不是type7本身的发送/接收时刻。

板不接受电脑重传的t2/t3；它们只能来自本板保存的有效DMA快照。type7不申请新的RX/TX时间戳，也不新增网络结果消息；本轮结果通过串口输出并与电脑记录联合验收。电脑sendto成功仅记本地提交成功，不能代替板端收到或计算成功。

## 板端记录和调度

现有DONE同时表示成功回报和失败终止，不能直接用于计算。本增量必须区分“REPORT发送返回OK且保存有效RX/TX”的记录与失败记录；只有前者可领取观测输入。原2000ms生命周期、4条容量和已处理键重复标记保持不变。

成功回报、提交完成和失败终止记录到期均安静清理；原WAIT_ACK/READY未完成记录到期仍按原规则计EXPIRED。旧模式没有提交type7属于正常行为，不能因此产生新过期错误。

- 完整键不匹配、记录已清理/过期或无有效双快照：拒绝，记NO_PAIR；不能从其它记录借时间。
- ACK尚未完成或REPORT尚未进入成功回报状态：拒绝，记EARLY，保留原正常交换流程。
- 首次合法提交把完整键、UID、原创建tick、t1/t4及本板RX/TX复制到独立4条CPU队列；不保留pbuf。原记录标记已领取，并保存两项电脑时刻用于短窗口重复判断。
- 相同键、相同t1/t4重复提交：忽略并计重复，不重复计算。相同键但t1/t4不同：计冲突，不覆盖已领取输入。队列满时计QUEUE_FULL，不复用旧输入。
- Process只在主循环执行，每次至多处理一项且结果日志最多1Hz；排队超过原2000ms生命周期的输入拒绝，不计算陈旧样本。原生测试覆盖tick回绕和延迟主循环。

新增App/Sync/sync_observation.c/.h，单向依赖现有估算器，不依赖LwIP、物理引脚或HAL。网络层只做解析、快照配对和有界入队；SyncObservation_Process调用原C函数。窗口显式固定800000000ns，与新电脑模式0.8秒总等待一致。

保留原C状态：倒序、越界、超窗及负路径时延均不能导出估算值。处理后不写PTP时间、addend或系统时钟，不输出LOCK。没有新的时钟源、定时器、ISR或DMA缓冲。

## 串口与电脑模式

成功日志拟为：

```text
$SYNC_OBS,SESSION=...,REQ_SEQ=...,CLIENT_TICK_MS=...,UID_W0=...,UID_W1=...,UID_W2=...,STATUS=0,OFFSET_X2_NS=...,DELAY_X2_NS=...,SYNC=0,PC=SW,BOARD=HW
```

状态0对应原C OK；其它C状态及本模块过期/入队失败用明确统计或拒绝记录表示，不附带前一次数值。统计至少区分合法/非法提交、无配对、提前、重复、冲突、队列满、计算成功/失败和格式错误。既有TS_IO、TS_PAIR及原业务计数的含义不变。

SESSION用两个32位十六进制字段拼接成16位文本。64位有符号结果通过有界整数转十进制文本后用%s输出，避免依赖尚未在本板验证的64位printf支持；测试包含INT64_MIN、半纳秒分子及最大值。成功行最坏含CRLF为226字节、含NUL为227，可使用现有256字节上限。全部格式化与串口发送在Process，不在输入/输出包装或ISR。

time_exchange_probe.py新增`--submit-observation`显式模式：仍先完成原request/ACK/REPORT配对，t4仍只取type5 ACK；生成完整样本后最多提交一次type7。原默认模式不发送type7，原type1～6解析和默认日志行为保持兼容，并有回归测试。

新模式额外记录本地提交事件和错误，hardware_verified仍为false；不能靠本地提交计数宣称板端通过。新增事件不伪装成原M2.2.3的纯采集窗口；旧归档数据及旧分析器输入格式保持不变。新模式联合验收直接读取其完整样本，通过M2.2.3已有真实C适配器计算参考，再按完整键与板端串口比较，不改写或删减原始文件来套用旧证据。

## 执行顺序与验收

1. 先为type7布局、完整键、tick标记和状态资格写失败测试；实现来源检查、成功回报状态及一次领取，不改变原type4～6行为。
2. 先测真实C结果与错误，再接入SyncObservation主循环队列和限速输出；测试无陈旧值、重复/冲突/提前/过期、容量满、tick回绕及整数格式边界。
3. 为电脑提交模式和默认模式兼容补测试；确认t4不被REPORT或提交事件替代，不自动重发、不混用不同会话。
4. 运行原219项及新增回归、Debug/Release构建/布局、统一PTP宏检查与独立复核；实际Generate Code回归保留用户源码及许可证。
5. 新ELF可审阅后取得该版本明确烧录/自动验收授权，沿用原ST-LINK配置校验复位，不改选项字节。
6. 联合采集新BOOT、COM3、旧5005接收70秒、旧5006请求30次和新模式30次交换；要求30组板端结果与真实电脑C结果的状态和两个整数分子逐条完全相同，键/来源正确，所有新旧异常计数0。
7. 原5005观察窗零缺口、旧30个ACK/RX/TX匹配、至少60条PTP及心跳连续；保留原文、固件/日志哈希和工具原summary。联合验收通过后以jxq提交并按已有协作授权推送，停止本增量。

新板端计算结果即使与电脑完全一致，也只证明本板观测运行链正确。最终双板同步的30秒收敛、±10μs波形差及后续声波测距仍需独立实测。
